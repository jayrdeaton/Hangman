# Hangman

An ad-free Hangman word-guessing game (Expo/React Native). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem. It depends on `@rific/auto-paper`, `@rific/drawer`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/scroll-view`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/sprites` (the `./fireworks` subpath only, for the win-celebration burst; see `src/effects/FireworksCelebration.tsx`), and `@tastic/hud` (the `./chrome` subpath only; see "Fleet chrome via `@tastic/hud/chrome`" below). `@tastic/sprites` was published as `@tastic/animations` until it was renamed; the old name is deprecated on npm, and Hangman switched on 2026-10-14 (the fireworks source is byte-identical). Still no Skia dependency: unlike the fleet's Skia-rendered games (BoxHockey, AirHockey, Snake), this app draws its gallows/word-reveal "modes" with `react-native-svg`, and `@tastic/sprites/fireworks` is itself SVG-based, so this app never depends on `@shopify/react-native-skia` at all. `@tastic/sprites` also has Skia-based subpaths (`./gravity`, `./shapes`, `./hockey`) that this app doesn't import; the package's subpaths keep each renderer's peer dependency scoped to only the apps that actually use it.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (42 suites, 463 tests)

npm run typecheck      # tsc

```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates:** the `build` and `update` scripts are plain `eas build` and `eas update`, with profiles in `eas.json` (`development`, `preview`, `production`). Pass the profile through, e.g. `npm run build -- --profile preview` or `npm run update -- --branch production --environment production --message "..."`. Nothing in them runs `verify`, so run `npm run verify` first. An OTA update also bumps `otaVersion` in `src/constants/release.ts` (the version label players see), committed before publishing. They used to be `@rific/updater`'s `rific-updater-build`/`rific-updater-update` bins, which @rific/updater 0.7.0 removed; the package stays for its OTA update hook. `build:web` is the one exception: it chains `npm run verify && expo export -p web` inline.

**A real regression, found and fixed as part of this migration: a manual mock under `src/__mocks__/` for a deep SUBPATH of a node_modules package is not reliably auto-applied the way a bare package-name mock is.** Every mock listed above for a *bare* package (`react-native-reanimated`, `expo-audio`, `redux-persist`, `@rific/scroll-view`, etc.) works with zero registration, matching this package's own documentation. But `2 of 30 suites` (`PackPuzzleList.test.tsx`, `PnpFlow.test.tsx`) started failing after the pure file-extraction pass, both on assertions sensitive to a react-native-paper `<Button icon='...'>`'s rendered text - instead of an empty icon slot, the raw MaterialCommunityIcons font glyph character showed up before the label. Confirmed directly, not guessed: a `console.warn` planted in the real (un-mocked) `@expo/vector-icons/build/MaterialCommunityIcons.js` and in react-native-paper's own compiled `MaterialCommunityIcon.js` fired during a failing test with a same-shaped mock file already sitting under `src/__mocks__/` for both, and did *not* fire once each was registered - and, separately, that `import * as RNPaper from 'react-native-paper'` (ESM, in real app/test code, transformed by `babel-preset-expo`) resolves to `react-native-paper/src/index.tsx`, while a plain `require.resolve('react-native-paper')` call resolves to `lib/commonjs/index.js` instead - two different real files, confirmed by the same technique. This app's own pre-migration `jest.setup.ts` never hit this, because it always registered every one of these subpaths with an explicit `jest.mock(path, factory)` call - the migration only moved the factory *bodies* out, and dropped the registration itself along with them. Fixed by keeping an explicit, no-factory `jest.mock('specifier')` call in `jest.setup.cjs` for every subpath mock (bare-package mocks still need none), so Jest is told to use the adjacent `src/__mocks__/` file rather than relying on auto-discovery. One further gap surfaced in the process and needed a fresh mock, not just a registration: `Theme.tsx` imports `@expo/vector-icons/MaterialCommunityIcons` (no `/build/`) directly to preload the icon font - a real module this app's own original `jest.setup.ts` never mocked either, but registering only the `/build/` subpath wasn't enough to stop *this* import from loading the real font-glyph component. That one is an inline factory in `jest.setup.cjs` rather than its own `src/__mocks__/` file, since a bare registration for it alone didn't reliably pick up an adjacent file either. **Flagged for Jay below** - this likely affects other already-migrated apps with subpath mocks (`redux-persist/integration/react`, `@expo/vector-icons/createIconSet`, etc.) that simply never had a test assertion sensitive enough to catch it.

**Migrating onto `@infinitetoken/tsconfig/expo` turned on `noUnusedLocals` for the first time**, surfacing 19 dead `import React from 'react'` statements (leftover from before the `react-jsx` transform made them unnecessary) across `App.tsx`, `src/__tests__/App.test.tsx`, `src/components/GameVisual.tsx`, `src/components/SketchWord.tsx`, and 15 of the `src/modes/*.tsx` visual-mode files - removed (three of them, `jenga.tsx`/`snowflakes.tsx`/`stars.tsx`, kept their `{ useState }` named import, only the default `React` import was dead). Also one dead reduce-callback parameter, `src/modes/letters.tsx:22`'s `(acc, w, i) =>` - `w` was never read (the running cursor uses `widths[i - 1]` instead) - renamed to `_w` rather than removed, since the used `i` parameter comes after it positionally.

**Migrating onto `typescript-eslint`'s `recommended` ruleset via the shared preset surfaced no new lint errors or warnings** - `npx eslint .` reports 0 problems both before and after the config swap.

`@infinitetoken/eslint-config` (`^0.2.0`), `@infinitetoken/jest-config` (`^0.2.3`), and `@infinitetoken/tsconfig` (`^0.4.1`) are all on real published versions - never yalc-linked for this app.

**`@rific/scroll-view` was briefly yalc-linked (`file:.yalc/@rific/scroll-view`) for a real bug - resolved 2026-09-11.** `ScrollViewProvider`'s `headerHeight` state could get stuck at `null` forever on web if a `<ScrollViewHeader>`'s `onLayout` simply never fired on the very first mount through Expo Router - every screen this app wraps in a `ScrollViewProvider` (`PackPuzzlesDrawer.tsx`, `PacksScreen.tsx`) stayed at `opacity: 0` until `headerHeight` resolved, so this was making this app's entire UI render invisible on first web load. Fixed in `ScrollViewProvider.tsx` itself with a `Platform.OS === 'web'`-gated effect that falls back to `setHeaderHeight(0)` two animation frames after mount if still `null` - see `React-Native-Scroll-View`'s own CLAUDE.md, "The web opacity-0 race `ScrollViewProvider` guards against," for the full reasoning. Now on the real published `@rific/scroll-view@0.7.1` (a patch - pure bug fix, no API change); the `.yalc/` link is gone.

## Testing

- Framework: Jest (`@infinitetoken/jest-config/expo`, `jest-expo` preset)
- Tests live in `src/__tests__/`, mirroring the source subfolder structure (`components/`, `effects/`, `hooks/`, `utils/`)
- Native/Expo module mocks live in `src/__mocks__/`, one file per module (including several scoped subpaths) - a bare-package mock is picked up automatically, but every subpath mock needs its matching explicit `jest.mock('specifier')` call in `jest.setup.cjs` too (see Tooling above for why)
- `jest.setup.cjs` holds only genuine setup-file concerns: the explicit subpath-mock registrations, process-level error handlers, the `IS_REACT_ACT_ENVIRONMENT` flag, and this app's own Animated-JS-driver-forcing + `NativeAnimatedModule` synchronous-callback patches. The RAF polyfills and no-factory `NativeAnimatedHelper` automock it used to carry were removed on 2026-10-02 as no-ops: `@react-native/jest-preset`'s own setup (pulled in by `jest-expo`, and run before this file) already defines `requestAnimationFrame`/`cancelAnimationFrame`, so the `typeof ... === 'undefined'` guards never fired, and `react-native/Libraries/Animated/NativeAnimatedHelper` doesn't exist in RN 0.86 (it moved to `src/private/animated/`), so that `jest.mock()` call always threw into a bare `catch` and never applied
- RNTL 14's `render`/`rerender`/`unmount`/`fireEvent` are all async: always `await` them. `render` only queues its tree for the automatic afterEach unmount once its own promise resolves, so an un-awaited `render` (App.test.tsx did this until 2026-10-13) leaves the whole app mounted, timers still firing, after the file's Jest environment is torn down.
- Nothing in an always-mounted subtree (the drawers stay mounted while closed) may run timers while hidden. ModePickerDrawer's card demo loop used to, so every test rendering Main or App fed React real-timer updates for as long as the tree lived. On a slow CI runner that turned one test hitting the 5s timeout into a whole file of timed-out tests and timed-out RNTL cleanup hooks, and CI run 37263959211 then hung until GitHub's 6-hour limit (fixed 2026-10-13: the loop pauses while the drawer is closed).

## OS portrait lock (2026-10-08)

Hangman is portrait-only and, unlike the @tastic games, draws no rotation of its own; nothing here lays out for a landscape window. It still takes `@tastic/core` for its Expo config plugin (`["@tastic/core", { "drawsRotation": false }]` in `app.json`'s `plugins`); its JS only arrives indirectly, through `@tastic/hud/chrome`, and nothing here mounts its `OrientationProvider` or draws rotation. The plugin owns the native lock: `orientation: "portrait"`; `ios.requireFullScreen` plus an iPad list of Portrait and UpsideDown (without it Expo forces all four iPad orientations and an iPad turned sideways got this portrait layout in a landscape window; the cost is Split View, Slide Over and Stage Manager); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). `drawsRotation: false` is what keeps UpsideDown on iPad: with no app-drawn rotation, iOS's own 180 flip is correct here, while the @tastic games list Portrait only because they draw the 180 themselves. Don't set any of those by hand. Check with `npx expo config --type introspect`; it only takes effect in a new native build (`ios/` and `android/` here are gitignored prebuild output, regenerated by `npx expo prebuild`).

## Fleet chrome via `@tastic/hud/chrome` (2026-10-15)

Hangman uses the fleet's shared UI from `@tastic/hud`, but only through its light `./chrome` subpath (added in hud 0.15.0 for this app). The main `@tastic/hud` entry also re-exports the per-seat lobby, `AchievementUnlockList` and the Skia gauge, so importing it would require Skia, `@tastic/profile` and `@tastic/split-screen`, none of which this app has. `eslint.config.cjs` blocks the bare `'@tastic/hud'` specifier with `no-restricted-imports`. `.npmrc`'s `legacy-peer-deps=true` means npm won't warn about a missing peer, so the lint rule and `npm ls @shopify/react-native-skia @tastic/profile @tastic/split-screen` (empty) are the guard. `@tastic/achievements` runs the app's stats and achievements (see "Achievements and stats" below); `tsc` also needs it because it type-checks hud's raw source (the `react-native` export condition) and `AchievementCatalogSection` type-imports it.

- **Update prompt:** `src/components/UpdateDialog.tsx` wraps hud's `UpdateDialog` (the fleet's Restart/Later card) and is mounted in `App.tsx` inside `Providers`, which it needs for the toast, Portal host and feedback-press `paper`. It owns the one automatic update check; `PuzzleDrawer`'s version text keeps a manual-only `useUpdater({ autoCheck: false })`. The card only appears in non-dev native builds (`@rific/updater` skips `__DEV__` and web).
- **Corners and Settings (2026-10-15):** the game screen uses hud's `CornerActionButtons` (plain `onSurface` glyphs: the Game Menu top-left, the Settings cog top-right) in place of the old filled red menu badge, and `PuzzleInfoRow`'s pills are padded and offset to sit level with and between them (the math is in its `hintSlot` comment). The cog opens `src/components/SettingsDialog.tsx`, a wrapper around hud's `BaseSettingsDialog` (Sound, Haptics, Appearance, version and Check for Updates) plus KEYBOARD and BACKUP sections (BACKUP is Export and Import of the unlocked puzzles, moved there from the old Achievements drawer in P11); Lock Orientation, Edge Guard and How to Play are deliberately not passed. Customize (`ModePickerDrawer`) keeps only the Color palette and the art carousel, and the Game Menu header is just "Hangman". Game is `locked` while Settings is open. `src/__mocks__/react-native-safe-area-context.ts` exposes `SafeAreaInsetsContext` as a real context because hud's `RotatedFrame` renders its Provider.
- **Confirm cards and Blur (2026-10-15, hud 0.17.0):** every confirm in the app (Import, Abandon, Delete pack, Reset achievements, and the pass-and-play hand-off's single Ready) is hud's `ConfirmDialog`; the local `ConfirmDialog.tsx` is gone. Since 0.17.0 its card is the theme's raised surface (auto-paper `BlurView`, elevation 3) over the theme's backdrop, blurred when the player's Blur setting is on. Because `Theme.tsx` passes `expoBlur`, Settings' APPEARANCE shows a Blur row on iOS and web (not Android), stored in redux with the rest of auto-paper's theme settings. Known upstream issue: tapping Blur remounts the open sheet (auto-paper's `BlurView` changes element type when blur flips), harmless in this portrait sheet. The corners pass `hitSlop={4}` (48pt targets). The prop (hud 0.16.0) only works on device with `@rific/feedback-press` 0.13.0+, which wraps Paper's IconButton in a Pressable that owns the slop; the same bump makes the drawer headers' existing `hitSlop={4}` real too.
- **Result card (2026-10-15):** `RoundEndDialog` is hud's `OverlayBackdrop`/`OverlayCard` in a Paper `Portal`, like Solitaire's win and loss banners: a primary trophy and "You Won!" or a muted skull and "You Lost!", the answer written left to right in the board's sketch letters (`SketchWord`'s `letterColors`/`letterDelaysMs`; missed letters red on a loss: `colors.error` in light mode, MD3's error tone 50 `#DC362E` in dark, since the theme's dark error is a pale pink), any unlocks and pack progress, then Next. No backdrop dismissal; Android back counts as Next. The card stops at the safe area and the answer, unlocks and progress scroll between the title and Next, so Next is always reachable; `fitAnswerFontSize` sizes the answer to the card's width and, down to 20, its height (the longest catalog answer fits a 375x667 phone without scrolling). `Game` hides the card and the fireworks itself on Next, because a shared-link puzzle's Next only opens the Game Menu over the same round.
- **Pass & Play prompt (2026-10-15):** `PnpWordPrompt` is the same card (DialogShell is gone): a primary "Pass & Play" title, a plain close glyph in the corner, the Word and Hint fields and Keep This Word, then a one-word Next. No backdrop dismissal; the close glyph and Android back open the Game Menu. It returns nothing while hidden but stays mounted, so its show/hide toggle survives a trip to the menu (the word itself lives in Main). It rises to clear the keyboard using React Native's own `Keyboard` events (reanimated's and keyboard-controller's keyboard hooks never reported a height in this build), measuring from the keyboard's real top edge (iOS heights include the home indicator, Android's leave out the navigation bar), and its height is capped to the room above the keyboard and inside the safe area, with the fields scrolling between the title and Next.
- **Root background:** loading any chrome component evaluates the whole `@tastic/core` barrel, and its `useThemedRootBackground.ts` calls `SystemUI.setBackgroundColorAsync('#000000')` at import, which blacks out the iOS window, the Android decor view and the web page body. `Theme.tsx`'s `RootBackground` repaints it with the theme's `surface` (the color `Main.tsx` paints behind every screen) once the theme exists and on every light/dark change. Don't also call core's `useThemedRootBackground`: its black/white would fight it.

## Achievements and stats via `@tastic/achievements` (2026-10-15)

Achievements are the fleet's package, not Hangman's own. The old AsyncStorage `achievements_v1` blob and `src/utils/achievements.ts` are gone, with no migration (the app was unreleased; Jay's call).

- **Stats** (`src/types/stats.ts`): one device-wide `StatsState` (no profiles): the solo record and its win streak, the Pass & Play record, flawless and no-hint win counts, modes won, completed built-in packs, custom packs created, letters, the day streak, and the first round's result and whether it was flawless. They change only through the pure funnel in `src/utils/statsEngine.ts` (`applySoloRound`, `applyPnpRound`, `applyCustomPackCreated`). Pass & Play never touches the solo record or streak. An abandoned round is a solo loss. Shared-link puzzles count as solo rounds. A win's `completedPackKeys` comes from `getCompletedBuiltInPackKeys` (`src/utils/unlocks.ts`), which rescans every built-in pack, so a pack finished through a backup import is credited on the next win; custom packs never count.
- **Catalog** (`src/constants/achievements.ts`, 34 entries): the fleet's first-game trio, the solve ladders (10/50/100 and 500/1,000/2,500), win streak, flawless, no hints, modes, packs completed, Pack Rat plus packs created, Pass & Play rounds (5/25/100) and days played. Jay's calls: no 5,000-plus ladder; `flawless_debut` keeps the fleet id and gold tier but means the first puzzle solved with no wrong guess; shared links count. **Ids are permanent once the app ships**: rename a title, never an id (`achievementCatalog.test.ts` pins the list). `VISIBLE_MODE_COUNT` is hardcoded (checked against the registry by the test) and a hidden mode won through a shared link doesn't count.
- **Store**: `src/redux/achievementsSlice.ts` (`createAchievementsSlice` with `isValidStats`/`migrateStats` from `src/utils/statsValidation.ts`) is mounted as `achievements` and **listed in the persist whitelist**; without that nothing persists. A corrupt stored blob falls back to defaults; one missing newer fields is filled in.
- **Provider** (`src/hooks/useGameStats.tsx`): `GameStatsProvider` calls `useAchievements` once (inside `PersistGate`, never keyed or gated: its mount re-sweeps the catalog) and puts only stable callbacks in context (`recordSoloRound`, `recordPnpRound`, `recordCustomPackCreated`, and `resetAll`, which also clears the unlocked puzzles), so a round never hands the always-mounted, memoized drawers new props. Data is read straight from the store, narrowly (`useUnlockedAchievementCount`, the Game Menu card) or only while on screen (`StatsScreen` mounts only while open).
- **Surfacing**: round unlocks are tier-colored rows on the result card (the achievement's icon, black on its bronze, silver or gold, beside its title); a new custom pack's unlocks, and an abandoned round's (no result card), use the fleet toast (title, 'Achievement unlocked', tier color and icon). No Hints Needed counts a win whenever the board offered its Hint pill (a pack label or a hint, PuzzleInfoRow's `hasHintContent`) and it wasn't opened. The catalog is listed on the Stats & Achievements screen (below). In light mode it draws progress bars and checks in the tier color darkened by half (gold and silver barely show on light surfaces); badges keep the true tier color.
- **Stats & Achievements screen (P11, 2026-10-16):** `src/components/StatsScreen.tsx` is hud's `BaseStatsScreen` (the shell Snake's and the other games' achievements screens use), titled Stats & Achievements: PROGRESS (puzzles unlocked and packs completed over PuzzleDrawer's own packsVersion-keyed manifest, custom packs included, passed in as a prop, the same array the All Packs row, the Pack Progress row and `PackProgressDrawer` count, so all of them agree; achievements earned; custom packs created), SOLO, PASS & PLAY (Rounds Played, Words Solved, Words Missed, Solve Rate), hud's `ActivityStatSection`, then ALL ACHIEVEMENTS built from `AchievementRow` (not `AchievementCatalogSection`, which can't take the light-mode `tierAccent`). A rate with nothing played shows "-". Its Reset All Stats confirm clears stats, achievements and unlocked puzzles (`useGameStats().resetAll`). The background is the theme's `surface` (the board's), text the fleet's black or white; on the web it keeps the game's 480pt column. With no routes yet, PuzzleDrawer hosts it: the Game Menu's card (now "Stats & Achievements") sets `statsVisible`, and it renders only while the menu is open too, as an absoluteFill layer at `STATS_SCREEN_Z_INDEX` (80, above every drawer tier) over the menu, which stays open underneath (hidden from accessibility) so Back returns to it; closing the menu clears it. The Game Menu has no Android back handling of its own, so StatsScreen registers a handler that returns to the menu (without it, back would leave the app); it takes the menu's already-loaded unlock map as a prop too. It knows nothing else about its host, so it can become a Home-screen page in P12+ as is. The old AchievementsDrawer is now `PackProgressDrawer` (every pack's progress, the drill-in and Random), opened from a "Pack Progress" row under the card whose subtitle counts complete packs (the trophies in the drawer), not puzzles, so it doesn't repeat the All Packs row. It takes the menu's manifest as a prop too (its own `[]`-memoized copy, inherited from AchievementsDrawer, was built before the custom-pack cache loaded, so it never listed a custom pack). The card's accessibility label sits on an accessible wrapper View, as in PackRow, since Paper's Card never hands it to its Pressable. hud's `BaseStatsScreen` header arrow has no accessibility label (an upstream gap; the test presses it as the screen's first button).
- **Tests** that render anything recording or reading stats need the app `store` plus `GameStatsProvider` (or the full `Providers`), and reset the slice in `beforeEach` (`store.dispatch(achievementsActions.reset())`), since the store is a module singleton.

## Status bar (2026-10-15)

Hangman mounts no status bar component and sets the bar nowhere: it never hid it, and its only `StatusBar` was auto-paper's Provider's (text colored from the theme). `@tastic/core`'s config plugin (0.14.0+) now sets `UIViewControllerBasedStatusBarAppearance: true` (the games need it to hide the bar per screen through react-native-screens, which this app doesn't use), and with it on every mounted React Native `StatusBar` logs an `RCTLogError` (a red box in dev). So `Theme.tsx` passes auto-paper's Provider `statusBar={false}` (0.13.2+, which also covers `Appbar.Header`), and expo-status-bar is gone (dependency and app.json plugin; the plugin did nothing without options). An app linked against the iOS 27 SDK couldn't set the bar through that component anyway: it only sets it app-wide through `UIApplication`, which UIKit ignores there. Pinned by `src/__tests__/statusBar.test.tsx` (no source file, `App.tsx` included, imports expo-status-bar or React Native's `StatusBar`; Theme turns auto-paper's off).

- **Behavior change, not fixed:** with no navigator, the bar takes the root view controller's default, whose text follows the SYSTEM appearance, not the in-app theme. A player who picks Light while the system is dark (or the reverse) gets status bar text in the wrong ink. In an Xcode 26 build that used to be right (auto-paper's `StatusBar` set it from the theme); in an Xcode 27 build it was already this way. A possible JS-only fix, untried: `Appearance.setColorScheme` from the resolved theme (it sets the window's `overrideUserInterfaceStyle`, which the default style follows), set back to `'unspecified'` in System mode so the theme keeps following the OS. It would also turn the keyboard and system alerts to the in-app theme.
- **It needs a new native build.** The Info.plist key only changes at prebuild, and the app.json plugin list changed too, so the fingerprint runtime version moves on: an OTA update from here on won't reach an older binary.
