# Hangman

An ad-free Hangman word-guessing game (Expo/React Native). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem. It depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/gestures` (`SwipeToDismiss`, for swiping Pass & Play seats away; see "Pass & Play sessions"), `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `react-native-sortables` (dragging Pass & Play seats into a new order, 2026-10-20; see "Pass & Play sessions" > The page), `@tastic/sprites` (the `./fireworks` subpath only, for the win-celebration burst; see `src/effects/FireworksCelebration.tsx`), `@tastic/hud` (the `./chrome` subpath only; see "Fleet chrome via `@tastic/hud/chrome`" below), and `@tastic/profile` (the fleet's player profiles, 0.16.2+: 0.16.1 added `OptionPickerOption`'s `color`, which the Single Player loadout's Difficulty rows use, and 0.16.2 tells a swatch renderer where it draws, so the chips stay flat; see "Players" below). `@tastic/sprites` was published as `@tastic/animations` until it was renamed; the old name is deprecated on npm, and Hangman switched on 2026-10-14 (the fireworks source is byte-identical). Still no Skia dependency: unlike the fleet's Skia-rendered games (BoxHockey, AirHockey, Snake), this app draws its gallows/word-reveal "modes" with `react-native-svg`, and `@tastic/sprites/fireworks` is itself SVG-based, so this app never depends on `@shopify/react-native-skia` at all. `@tastic/sprites` also has Skia-based subpaths (`./gravity`, `./shapes`, `./hockey`) that this app doesn't import; the package's subpaths keep each renderer's peer dependency scoped to only the apps that actually use it.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v58.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 58 specifically (and expo-router 58: see "Routes and resume" below).

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (80 suites, 1442 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
npm run build:web       # verify, then the web export for games.infinitetoken.com/hangman/
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates:** the `build` and `update` scripts are plain `eas build` and `eas update`, with profiles in `eas.json` (`development`, `preview`, `production`). Pass the profile through, e.g. `npm run build -- --profile preview` or `npm run update -- --branch production --environment production --message "..."`. Nothing in them runs `verify`, so run `npm run verify` first. An OTA update also bumps `otaVersion` in `src/constants/release.ts` (the version label players see), committed before publishing. They used to be `@rific/updater`'s `rific-updater-build`/`rific-updater-update` bins, which @rific/updater 0.7.0 removed; the package stays for its OTA update hook. `build:web` is the one exception: it chains `npm run verify &&` before the web export (see "Web on games.infinitetoken.com" below).

**A real regression, found and fixed as part of this migration: a manual mock under `src/__mocks__/` for a deep SUBPATH of a node_modules package is not reliably auto-applied the way a bare package-name mock is.** Every mock listed above for a *bare* package (`react-native-reanimated`, `expo-audio`, `redux-persist`, `@rific/scroll-view`, etc.) works with zero registration, matching this package's own documentation. But `2 of 30 suites` (`PackPuzzleList.test.tsx`, `PnpFlow.test.tsx`) started failing after the pure file-extraction pass, both on assertions sensitive to a react-native-paper `<Button icon='...'>`'s rendered text - instead of an empty icon slot, the raw MaterialCommunityIcons font glyph character showed up before the label. Confirmed directly, not guessed: a `console.warn` planted in the real (un-mocked) `@expo/vector-icons/build/MaterialCommunityIcons.js` and in react-native-paper's own compiled `MaterialCommunityIcon.js` fired during a failing test with a same-shaped mock file already sitting under `src/__mocks__/` for both, and did *not* fire once each was registered - and, separately, that `import * as RNPaper from 'react-native-paper'` (ESM, in real app/test code, transformed by `babel-preset-expo`) resolves to `react-native-paper/src/index.tsx`, while a plain `require.resolve('react-native-paper')` call resolves to `lib/commonjs/index.js` instead - two different real files, confirmed by the same technique. This app's own pre-migration `jest.setup.ts` never hit this, because it always registered every one of these subpaths with an explicit `jest.mock(path, factory)` call - the migration only moved the factory *bodies* out, and dropped the registration itself along with them. Fixed by keeping an explicit, no-factory `jest.mock('specifier')` call in `jest.setup.cjs` for every subpath mock (bare-package mocks still need none), so Jest is told to use the adjacent `src/__mocks__/` file rather than relying on auto-discovery. One further gap surfaced in the process and needed a fresh mock, not just a registration: `Theme.tsx` imports `@expo/vector-icons/MaterialCommunityIcons` (no `/build/`) directly to preload the icon font - a real module this app's own original `jest.setup.ts` never mocked either, but registering only the `/build/` subpath wasn't enough to stop *this* import from loading the real font-glyph component. That one is an inline factory in `jest.setup.cjs` rather than its own `src/__mocks__/` file, since a bare registration for it alone didn't reliably pick up an adjacent file either. **Flagged for Jay below** - this likely affects other already-migrated apps with subpath mocks (`redux-persist/integration/react`, `@expo/vector-icons/createIconSet`, etc.) that simply never had a test assertion sensitive enough to catch it.

**Migrating onto `@infinitetoken/tsconfig/expo` turned on `noUnusedLocals` for the first time**, surfacing 19 dead `import React from 'react'` statements (leftover from before the `react-jsx` transform made them unnecessary) across `App.tsx`, `src/__tests__/App.test.tsx`, `src/components/GameVisual.tsx`, `src/components/SketchWord.tsx`, and 15 of the `src/modes/*.tsx` visual-mode files - removed (three of them, `jenga.tsx`/`snowflakes.tsx`/`stars.tsx`, kept their `{ useState }` named import, only the default `React` import was dead). ## Testing

- Framework: Jest (`@infinitetoken/jest-config/expo`, `jest-expo` preset)
- Tests live in `src/__tests__/`, mirroring the source subfolder structure (`components/`, `effects/`, `hooks/`, `utils/`)
- Native/Expo module mocks live in `src/__mocks__/`, one file per module (including several scoped subpaths) - a bare-package mock is picked up automatically, but every subpath mock needs its matching explicit `jest.mock('specifier')` call in `jest.setup.cjs` too (see Tooling above for why)
- `jest.setup.cjs` holds only genuine setup-file concerns: the explicit subpath-mock registrations, process-level error handlers, the `IS_REACT_ACT_ENVIRONMENT` flag, and this app's own Animated-JS-driver-forcing + `NativeAnimatedModule` synchronous-callback patches. The RAF polyfills and no-factory `NativeAnimatedHelper` automock it used to carry were removed on 2026-10-02 as no-ops: `@react-native/jest-preset`'s own setup (pulled in by `jest-expo`, and run before this file) already defines `requestAnimationFrame`/`cancelAnimationFrame`, so the `typeof ... === 'undefined'` guards never fired, and `react-native/Libraries/Animated/NativeAnimatedHelper` doesn't exist in RN 0.86 (it moved to `src/private/animated/`), so that `jest.mock()` call always threw into a bare `catch` and never applied
- RNTL 14's `render`/`rerender`/`unmount`/`fireEvent` are all async: always `await` them. `render` only queues its tree for the automatic afterEach unmount once its own promise resolves, so an un-awaited `render` (App.test.tsx did this until 2026-10-13) leaves the whole app mounted, timers still firing, after the file's Jest environment is torn down.
- Anything that reads the active player (stats, rounds, puzzle unlocks, art, difficulty, packs, colors) needs the app `store`; reset `activePlayer`, `playerSettings`, `playerTheme` and `profiles` (`profilesActions.setAll([])`) (and `round`, `achievements`) in `beforeEach`, and give a hand-built test store the `activePlayer` reducer. Choose Packs' tests (and its pages') wrap in the store and `CatalogProvider`. A profile made active before `Providers` mounts has to be on the roster, or `ProfilesProvider`'s launch reconcile forgets it and the guest plays. At the Pass & Play table (its page and games) a guest seat plays as its own guest, `guestSeatKey(seatId)`, never `GUEST_PLAYER_KEY`: seed a table guest's picks, colors and rounds under the seat's key, and the active player reads `{ profileId: null, seatId }`. Under Jest there is no shared roster (no App Group module, not the web), so the roster is the store's own copy; `useProfiles.test.tsx` fakes the shared store at its native end (expo-modules-core's `TasticProfile` module) to run the package's real sync. @tastic/profile's pickers only show their popover once hud's `useAutoAlign` has measured the trigger, and the jest preset's View never answers `measureInWindow`, so a test that opens one spies `View.prototype.measureInWindow` to call back (see `LoadoutScreen.test.tsx`).
- A test that renders auto-paper's `Provider` passes `statusBar={false}`, as `Theme.tsx` does. Otherwise it renders React Native's own `StatusBar`, whose update is a `setImmediate`. Under fake timers on Node 22 (what CI runs), every later `render` in that file then never settles: the test hits its 5s timeout, and so does every one after it. Node 26 doesn't hang, so it passed locally (fixed 2026-10-20, after the v1.0.1 Deploy and CI runs failed in HeroTitle and SettingsDialog). Before trusting a local pass on a timing-sensitive suite, run it under Node 22 too (`npx -y node@22 node_modules/.bin/jest <file>`).
- `src/__mocks__/react-native-reanimated.ts` animates nothing: `Animated.View` is React Native's own View (so a test reads `entering`, `exiting` and `layout` straight off it), the layout animation presets (`FadeIn`, `ZoomIn`, `LinearTransition`, ...) are builders whose every modifier hands back the same builder, `LayoutAnimationConfig` renders its children, `withTiming` hands back its target, and `useReducedMotion` is a `jest.fn` returning false. A test that turns Reduce Motion on puts it back after (`jest.clearAllMocks` keeps a `mockReturnValue`). To watch `withTiming`, mock the module with a factory over the mock file (`useEasedValue.test.ts`): a spy on the imported module doesn't reach the hook's own import.
- Nothing in an always-mounted subtree (Choose Packs and its pages stay mounted while away, and Home and the loadout stay mounted under the screens pushed over them) may run timers while hidden. ModePickerDrawer's card demo loop used to, so every test rendering the old Main or App fed React real-timer updates for as long as the tree lived. On a slow CI runner that turned one test hitting the 5s timeout into a whole file of timed-out tests and timed-out RNTL cleanup hooks, and CI run 37263959211 then hung until GitHub's 6-hour limit (fixed 2026-10-13: the loop pauses while the drawer is closed). Its carousel is back on the Single Player loadout (`ArtCarousel`, 2026-10-18), where it plays while the page is in view, so the loadout's screen tests stub the whole carousel (`LoadoutScreen.test.tsx`, which reads only whether the page paused it) and its own suite stubs the loop (`ArtCarousel.test.tsx`).

## OS portrait lock (2026-10-08)

Hangman is portrait-only and, unlike the @tastic games, draws no rotation of its own; nothing here lays out for a landscape window. It still takes `@tastic/core` for its Expo config plugin (`["@tastic/core", { "drawsRotation": false }]` in `app.json`'s `plugins`); its JS only arrives indirectly, through `@tastic/hud/chrome`, and nothing here mounts its `OrientationProvider` or draws rotation. The plugin owns the native lock: `orientation: "portrait"`; `ios.requireFullScreen` plus an iPad list of Portrait and UpsideDown (without it Expo forces all four iPad orientations and an iPad turned sideways got this portrait layout in a landscape window; the cost is Split View, Slide Over and Stage Manager); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). `drawsRotation: false` is what keeps UpsideDown on iPad: with no app-drawn rotation, iOS's own 180 flip is correct here, while the @tastic games list Portrait only because they draw the 180 themselves. Don't set any of those by hand. Check with `npx expo config --type introspect`; it only takes effect in a new native build (`ios/` and `android/` here are gitignored prebuild output, regenerated by `npx expo prebuild`).

## Icons and splash (2026-10-13)

Seven games (AirHockey, BoxHockey, Hangman, LightCycles, Pong, Snake, Solitaire) and Expo-Starter use the same four files, `assets/images/icon-light.png`, `icon-dark.png`, `splash-light.png` and `splash-dark.png`, and the same `app.json` config. The icons are opaque 1024px squares on `#FAFAFA` (light) and `#050505` (dark). Each splash is its icon's art on a transparent background. The `expo-splash-screen` plugin paints the same two colors behind it, at `imageWidth` 200. `expo.icon` is `icon-dark.png`, `web.favicon` is `splash-dark.png`, `ios.icon` is the dark/light pair, and there is no Android `adaptiveIcon` (Android uses `expo.icon`). The favicon is the transparent splash art, not the opaque icon, because it looks better in a browser tab (2026-10-16), so `splash-dark.png` has to read on both light and dark tabs. Snake is the only game whose light and dark art differ (its body and head fill). The other games keep two identical splash files so the config is the same everywhere. Icon and splash changes only take effect in a new native build.

## Status bar (2026-10-15)

Hangman mounts no status bar component: its only `StatusBar` was auto-paper's Provider's (text colored from the theme). `@tastic/core`'s config plugin (0.14.0+) sets `UIViewControllerBasedStatusBarAppearance: true` (the games need it to hide the bar per screen through react-native-screens), and with it on every mounted React Native `StatusBar` logs an `RCTLogError` (a red box in dev). So `Theme.tsx` passes auto-paper's Provider `statusBar={false}` (0.13.2+, which also covers `Appbar.Header`), and expo-status-bar is gone (dependency and app.json plugin; the plugin did nothing without options). An app linked against the iOS 27 SDK couldn't set the bar through that component anyway: it only sets it app-wide through `UIApplication`, which UIKit ignores there. Pinned by `src/__tests__/statusBar.test.tsx` (no source file imports expo-status-bar or React Native's `StatusBar`; Theme turns auto-paper's off).

- **Fixed by the router pass (2026-10-17), unverified on device:** from 2026-10-15 until the router pass, with no navigator, the bar took the root view controller's default, whose text follows the SYSTEM appearance, not the in-app theme (a player who picked Light while the system was dark got status bar text in the wrong ink). ## Players (2026-10-17)

Everything belongs to a player (Jay, 2026-10-17: his kids play a puzzle, then hand him the device): stats and achievements, unlocked puzzles, the waiting solo round, colors, art, difficulty and pack selection. Keyboard, sound and haptics stay device-wide. A player is a profile from the fleet's shared roster (`@tastic/profile` 0.16+, the same profiles as every @tastic game) or the guest. ## Keep Awake (2026-10-17)

Jay chose to give Hangman Keep Awake (keep the screen from locking during a round: the OS auto-lock only counts touches, so a long think on a guess, or a Pass & Play hand-over, can lock a release build). `/game` (`src/app/game.tsx`'s `GameRoute`) calls `@rific/core`'s `useKeepAwake('game')`, released on unmount, unless the player turns off the Keep Awake row in Settings (default on, read live so the toggle applies mid-round). Expo only keeps the screen awake by itself in development builds.

- **The setting is core's:** `keepAwakeReducer` is mounted as `keepAwake` in `store.ts` and listed in the persist whitelist, and `Providers.tsx`'s `KeepAwakeBridge` (`initialValue` from the slice, `onChange` dispatching `keepAwakeActions.initialize`, the same bridge as the other games) mounts core's `KeepAwakeProvider` with `expoKeepAwake={ExpoKeepAwake}` (`import * as ExpoKeepAwake from 'expo-keep-awake'`), directly inside PersistGate so it is above every Portal.Host. Handing it the module is what turns the feature on: without it `useKeepAwake` does nothing and hud hides the row. A first per-game version (its own settings slice and `useSettings` hook, which also left `SettingsDialog.test.tsx` and `PnpFlow.test.tsx` red without a store) was reverted the same day in favor of this. Those tests render `SettingsDialog` with no provider and still pass: core's context falls back to an inert default (setting on, no module), so the row just stays hidden there.
- The row is `@tastic/hud`'s (0.23.0+): `BaseSettingsDialog` reads core's setting itself, with no props, and shows the row (caption "Stop auto-lock mid-match") only when `useExpoKeepAwake()` returns a module and the device is touch-first (native and touch-first browsers). Needs `@rific/core` 0.4.0+.
- `expo-keep-awake` is a direct dependency (`~58.0.3`, via `npx expo install`). It was already in native builds as a dependency of `expo`, so no new native build is needed.

## Web on games.infinitetoken.com (2026-10-19)

The web build is served at https://games.infinitetoken.com/hangman/ with every other Tastic game on that one origin, so they share browser storage and, through it, `@tastic/profile`'s player roster (the web side of the App Group). Games-Web, the hub, proxies `/hangman/*` to this project's own production deployment (`origin` `https://hangman-teal-psi.vercel.app` in its `src/constants/site.ts`; see its CLAUDE.md). It's the setup Snake, Solitaire, LightCycles and BoxHockey have. Hangman was the one game still on its old root build until 2026-10-19: the hub's page loaded `/_expo/...` from the hub's root, which 404s, so players got a blank page that answered 200 (the site-alignment check's live-hub row, 2026-10-18).

- **The build:** `build:web` runs `verify`, then `WEB_BASE_URL=/hangman expo export -p web --output-dir web-build/hangman`. `app.config.ts` (the same file in every game on the hub) turns `WEB_BASE_URL` into `experiments.baseUrl` only when it's set: a base URL also reaches native bundles, asset paths and EAS updates, so it never goes in `app.json`. Expo writes the export flat and prefixes the URLs inside it, so the output folder is what puts the files under `/hangman/`, and this project's own deployment serves the same paths the hub forwards. Building more than one game locally: one at a time with `--clear`, or Metro's shared cache leaks one app's config into the next.
- **`vercel.json`** is the other games' file, byte for byte: `buildCommand` `npm run build:web`, output `web-build`, `cleanUrls` on, and a `/<game>/...` path that isn't a file rewrites to `/<game>/index`, the path `cleanUrls` gives `index.html` (the form Vercel's instant static serving answers). With `single` output that one page is every route, `/hangman` itself included (the hub forwards its `/hangman/` there). The old `hangman.infinitetoken.com` (still attached to this project) redirects to the same path under `games.infinitetoken.com/hangman/`, query string kept, so a share link made there (`/play?phrase=...`) still opens its puzzle; its `/privacy` goes to the hub's privacy page. The project's own root `/` is a 404 now, as Snake's is. It replaced Hangman's own file (no `cleanUrls`, `/(.*)` to `/index.html`, `/privacy` to `privacy.html`).
- **Privacy and store links:** `public/privacy.html`, a copy of the shared Tastic policy, is gone. The one policy is the hub's `/privacy`, and `store.config.json` points there, with support at `/support` and marketing at `/hangman`.
- **Routes and share links:** expo-router adds and strips the base URL itself, so routes, `router.push`, `Redirect` and incoming `/hangman/play?...` links need nothing. `Linking.createURL` on the web builds from the page's origin alone, so `buildPuzzleLink` (`src/utils/puzzleLink.ts`, with no caller right now) puts `/play` under the inlined `process.env.EXPO_BASE_URL` on the web; native links stay `hangman://play`. `.hangman` files are native only (`+native-intent`, `IncomingFileImport`); on the web Backup is a blob download and a file input, with no URL involved.
- **Storage:** every key this game writes starts with `STORAGE_PREFIX`, `'hangman:'` (`src/constants/storage.ts`): redux-persist's `keyPrefix` on both blobs (`hangman:root` and `hangman:round`, in place of the `persist:root` that on one origin would be another game's; REHYDRATE still reports `root` and `round`), the unlocks (`hangman:puzzle_unlocks_v1:<playerKey>`), the custom packs (`hangman:custom_packs_v1`), and `hangman:autoSaveCustom`, `hangman:keyboardLayout` and `hangman:packPuzzleListPrefs`. A new key takes it too. It applies on native as well, as in the other games: saves under the old keys are left in storage and never read (no migrations; Hangman hadn't shipped), so a device's progress starts fresh with the first build or update that has it. On the web the one other key is @tastic/profile's roster, `group.com.infinitetoken.tastic:sharedProfiles`, shared on purpose. Pinned by `store.test.ts` and `unlocks.test.ts`.
